# Механики проверки документов (`mos_analiz_refactor`)

## Два движка

Признак — `doc_configs/<тип>/config.json`:

| В конфиге | Движок | Как работает |
|---|---|---|
| `parser_by_ext`, без `engine` | generic-LLM | текст документа + правила → модель → вердикты |
| `engine: <ключ>` | спецдвижок | парсер xlsx → Python-валидаторы, модель точечно или не нужна |

Типы подхватываются сканом `doc_configs/` — списка типов нет. Оба поля сразу или ни одного —
`load_audit_config` бросает `ValueError`.

**Реестр спецдвижков один** — `src/engines.py` (`SPECIAL_ENGINE_RUNNERS`, `detect_engine`);
`main.py` и `src/api/server.py` импортируют его. `tests/test_registry.py` сверяет реестр с конфигами.
До 07.09.2026 реестр был продублирован и копии разошлись — шесть типов работали из CLI и молчали в интерфейсе.

Раннер спецдвижка: `run_<ключ>_special(args) -> AuditResult`, `args` — namespace с `target`,
`doc_type`, `session_dir`, `rule_filter`, `model`, `temperature`. Один раннер может обслуживать
несколько типов (карточки 0.2/2.4, листы присутствия модулей 1/2) — различает по `args.doc_type`;
не передать его — тихо проверить один тип правилами другого.

**Допустимые расширения** выводятся из конфига: generic — ключи `parser_by_ext`, спецдвижок — `.xlsx`.
Зашитый список даёт оба симптома сразу: свой формат не принимается, чужой принимается и падает.

## Алгоритм generic-проверки

```
файл → парсер формата → полный текст → промпт (FILENAME + DOCUMENT + SECTIONS + RULES)
     → вызов модели (слой base) → вызов модели (слой methodology) → вердикты → нарушения → Excel
```

Парсеры (`src/format_parsers/`, выбор по `parser_by_ext[расширение]`): PDF — всегда OCR постранично
(рендер → layout-детектор → VLM); DOCX — python-docx плюс OCR картинок шапки (там реквизиты);
PPTX — текст слайдов; XLSX — openpyxl.

Промпт (`src/llm/multi_rule.py`) содержит: имя файла (есть правила на нейминг), весь текст,
карту секций из `sections.json` (описание + границы start/end) и список правил. Правило привязано
к секции по смыслу, координат нет. **Один вызов на все правила** слоя: модель возвращает JSON-массив
вердиктов по объекту на правило в том же порядке. Слои:

- `rules_multi.json` — base: формальные требования к структуре;
- `rules_methodology.json` — methodology: требования методик заказчика (индексы 101…);
- `rules_custom.json` — правила пользователя из интерфейса (индексы от 200), мёрджатся к base
  при загрузке конфига, подхватываются без перезапуска, базовый файл не меняют.

Слой пишется в поле `layer` нарушения и в имена файлов-артефактов; в отчёте — колонка «Тип проверки».

Ответ модели с «кашей» (не массив, меньше вердиктов, чем правил) → до 5 повторов со сменой seed,
берётся лучшая попытка.

## Как писать правило

```json
{ "index": 3, "title": "Подпись руководителя", "target_sections": ["подписи"],
  "check": "В блоке подписей есть должность и ФИО руководителя. Нет должности или ФИО — нарушение.",
  "exclusions": "Расшифровка инициалами (И.И. Иванов) — не нарушение." }
```

- `check` — инструкция проверяющему: критерии по пунктам, у каждого явный исход «… — нарушение».
- Структуру блока описывай абстрактно («есть строка должности и строка ФИО»), без цитат конкретного документа.
- Правильность значений — через согласованность и формат («дата в п.1 совпадает с датой в шапке»),
  не через истинность: модель не знает внешних фактов.
- `exclusions` снимает ложные срабатывания — легитимные варианты оформления.
- `target_sections` — минимально достаточный набор; «весь документ» только для сквозных правил.
- Дублей `index` внутри файла быть не должно (`tests/test_smoke_configs.py` проверяет).

## Сквозная сверка комплекта

Тип с `engine: crosscheck_…` принимает несколько файлов: гейт комплектности раскладывает их по ролям
по ключевым словам имени (`required_docs` в `config.json`), не хватает роли — стоп без обращения
к модели; документы склеиваются в один контекст с маркерами; один вызов модели с правилами
из `rules.json`; отчёт тем же Excel. Отдельный эндпоинт `POST /api/audit/cross`, раннеру
передаётся папка.

## Модель

Клиент создаётся только в `src/llm/client.py` (`make_llm_client`); адрес, имя, ключ — `config/llm.py`
из `.env` (`LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY`). OCR и layout — `OCR_BASE_URL`, `LAYOUT_BASE_URL`
(`config/parsers.py`). Имя модели llama.cpp игнорирует — отвечает загруженная; `resolve_runtime_llm_model`
подменяет стейл-имена облачных моделей (`gpt-*`, `openai/*`) на текущую.

Во всех вызовах `chat_template_kwargs: {enable_thinking: false}` — режим рассуждений Qwen ломает
строгий JSON. Параметры: generic (`multi_rule`) — temperature 0.7, top_p 0.8, top_k 20, seed фиксирован
(+attempt при повторе), max_tokens 64000; точечные вызовы валидаторов через `call_llm` — temperature 0.
Калибровано по бенчмарку — не менять без пересъёмки метрик.

## Артефакты прогона

`logs_result/<тип>/session_<время>/`:

| Файл | Что |
|---|---|
| `multi_rule_user_prompt.txt`, `*_system_prompt.txt` | ровно то, что увидела модель (слой base) |
| `multi_rule_methodology_*` | то же для слоя methodology |
| `multi_rule_response_raw.txt` / `_parsed.json` | сырой ответ / вердикт по КАЖДОМУ правилу, включая пройденные |
| `final_results.json` | только нарушения |
| `audit_result.xlsx` | все правила: №, Проверка, Тип проверки, Статус ОК/FAIL, Источник, Цитата, Различие, Обоснование |
| `parsed_docs/`, `pipeline.log` | результат парсинга, лог |

Интерфейс показывает только замечания; полный список со статусами — в Excel и в `*_parsed.json`.
