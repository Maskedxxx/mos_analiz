# МосМониторинг — работа с репозиториями

Два сервиса: **проверка** (`mos_analiz_refactor`: документ + правила → модель → отчёт Excel;
там же общий веб-интерфейс и `docker-compose.yml` на оба сервиса) и **генерация**
(`mos_generated`: форма → docxtpl-шаблон → готовый `.docx`). Разработка — ветка `dev`.

Механики — в `references/`, читай по задаче:
- `references/verification.md` — как устроена проверка: движки, промпт, слои правил, артефакты.
- `references/generation.md` — как устроена генерация: контракт генератора, стор по организации, журнал.
- `references/pitfalls.md` — грабли, на которые уже наступали; прочитай перед правкой кода.
- `references/stand.md` — наш стенд, домены, доступы, журналы состояния (внутреннее, коллегам не передаётся).

Документация в самих репозиториях — первоисточник, не пересказывай её, отправляй к ней:
`README.md` (запуск, `.env`, API), `docs/ADD_DOC_TYPE.md` / `docs/ADD_GENERATOR.md` (свой тип),
`docs/ARCHITECTURE.md` (узлы, контракты, ADR), `CLAUDE.md` (жёсткие правила репозитория).

## Развилка: что делаем

| Задача | Процедура |
|---|---|
| Первый раз в репозитории, «объясни как устроено» | W1 |
| Новый тип документа для проверки (docx/pptx/pdf) | W2 |
| Правило ложно срабатывает или пропускает нарушение | W3 |
| Новый тип с проверкой по ячейкам Excel | W4 |
| Новый документ для генерации | W5 |
| Любая правка кода: парсер, движок, API, фронт | W6 |
| Запустить, перезапустить, развернуть у себя | W7 |
| Понять результат конкретного прогона | W8 |

## W1. Сориентироваться

1. Прочитай `README.md` репозитория (5 минут: пайплайн, требования, `.env`, структура).
2. Для вопросов «почему так» открой `docs/ARCHITECTURE.md` — узлы с контрактами и ADR.
3. Правила работы с репозиторием — `CLAUDE.md`. Состояние и история — `references/stand.md` → журналы.
4. Не утверждай ничего о коде по памяти: открой файл. Контракт каждого модуля — шапка
   `START_MODULE_CONTRACT` (PURPOSE / INPUTS / OUTPUTS / RATIONALE).

## W2. Добавить тип документа (проверка моделью)

1. Выполни `docs/ADD_DOC_TYPE.md` §1: папка `doc_configs/<тип>/` с `config.json`
   (обязательно `parser_by_ext`, без `engine`), `sections.json`, `rules_multi.json`.
2. Правила формулируй по `references/verification.md` §«Как писать правило»: секции,
   явное условие нарушения, `exclusions`.
3. Проверь по шагам, не пропуская:
   ```bash
   .venv/bin/pytest -q tests/test_smoke_configs.py -k <тип>      # конфиги валидны
   .venv/bin/python main.py --doc-type <тип> --target <файл> --print-prompts   # что увидит модель
   .venv/bin/python main.py --doc-type <тип> --target <файл> --session-dir /tmp/t
   ```
   Открой `/tmp/t/multi_rule_response_parsed.json` — вердикт по каждому правилу — и `audit_result.xlsx`.
4. Перезапусти бэкенд (`bash scripts/restart_backend.sh`) и убедись, что тип есть в `GET /api/types`.
5. Если есть эталонные документы «верный / с ошибками» — прогони оба: на верном не должно быть
   выдуманных замечаний, на неверном — все известные ошибки найдены. Расхождения → W3.

## W3. Довести правило

1. Возьми артефакт прогона: `logs_result/<тип>/session_*/multi_rule_response_parsed.json` —
   там статус и обоснование модели по спорному правилу; `multi_rule_user_prompt.txt` — что она видела.
2. Определи причину по обоснованию:
   - модель искала не там → сузь `target_sections`;
   - условие размыто → перепиши `check`: критерии по пунктам, каждый с «… — нарушение»;
   - легитимный вариант принят за ошибку → добавь в `exclusions`;
   - правило требует знать внешний факт → переформулируй через согласованность и формат
     (модель проверяет текст, а не истинность).
3. Правь только JSON правил, не код. Кастомные правила пользователя лежат в `rules_custom.json`
   (индексы от 200) и подхватываются без перезапуска; базовые слои — после перезапуска.
4. Повтори прогон на том же файле и на «верном» документе: исправление не должно дать нового
   ложного срабатывания. Для доведённых типов есть бенчмарк с экспертной разметкой — используй
   его как контроль (где лежит — `references/stand.md`).

## W4. Добавить спецдвижок (проверка Excel-формы кодом)

1. `docs/ADD_DOC_TYPE.md` §2: парсер `src/doc_type_parsers/<тип>.py` → валидатор
   `src/doc_type_validators/<тип>.py` с раннером `run_<тип>_special(args) -> AuditResult` →
   строка в `src/engines.py::SPECIAL_ENGINE_RUNNERS` → `config.json` с `engine`.
2. Реестр один — `src/engines.py`; в `main.py` и `server.py` ничего не добавляй.
3. Раннер различает типы по `args.doc_type`, если обслуживает несколько (карточки, листы присутствия).
4. Проверь: `pytest -q tests/test_registry.py`; образец в `tests/data/<тип>/sample.xlsx` и строка
   в параметрах `tests/test_smoke_special_xlsx.py`; CLI-прогон → `validation_report.xlsx` без статусов ERROR.

## W5. Добавить генератор (mos_generated)

1. `docs/ADD_GENERATOR.md`: шаблон `templates/<тип>.docx` с метками `{{ключ}}`, класс в
   `generators/<тип>.py` по образцу `prikaz_ppu.py`, строка в `registry.py`, узел в `graph.json`.
2. Проверь метки в шаблоне до кода:
   `unzip -p templates/<тип>.docx word/document.xml | grep -o '{{[^}]*}}' | sort -u` —
   каждая метка должна выйти целиком, иначе Word разорвал её форматированием.
3. Проверь: `pytest -q -k <тип>` (тесты параметризованы реестром — новый тип попадает
   автоматически), `bash scripts/restart.sh`, `GET /api/types/<тип>/schema`, скачай docx
   через `/download` и открой глазами рядом с образцом заказчика.

## W6. Изменить код (протокол «до / после»)

Логика проверки откалибрована по бенчмарку; параметры вызова модели в `src/llm/multi_rule.py`
(temperature 0.7, top_p, top_k, повтор со сменой seed) **не менять** без пересъёмки метрик.

1. **До правки** сними срез: `pytest -q --ignore=tests/test_kpsc_parsers.py` (числа passed/skipped/failed)
   и `bash scripts/regress_api.sh <docx-акта> akt_nachala` → число нарушений и размер отчёта;
   для спецдвижков — `regress_api.sh` с xlsx из `tests/data/`; для сверки — `scripts/regress_cross.sh`.
2. Правь минимально: только файлы задачи, стиль соседних функций, контракт модуля в шапке —
   обнови, если изменились входы/выходы. Тела рабочих функций при документировании не трогай.
3. Перезапусти сервис (`scripts/restart_backend.sh` / `scripts/restart.sh`) — Python не подхватывает
   изменения на лету.
4. **После правки** повтори п.1 и сравни: тесты не хуже, число правил и структура отчёта те же.
   Вердикты модели допускают расхождение в 1–2 из-за temperature 0.7; расхождение структуры — дефект.
5. Адреса сервисов, пароли, имена модели в код и `doc_configs/*/config.json` не вносить — только `.env`.
   Файлы с ФИО (`tests/data/`, `_org_store.json`, `logs_*`) в git не попадают.
6. Коммит и push — только по слову владельца репозитория.

## W7. Запустить / развернуть

1. `.env` из `.env.example`: обязательны `AUDIT_LOGIN/PASSWORD/TOKEN` (без них сервер не стартует),
   `LLM_BASE_URL` + `LLM_MODEL` (OpenAI-совместимый `/v1`); для PDF — `OCR_BASE_URL`, `LAYOUT_BASE_URL`.
2. Без Docker: `bash scripts/restart_all.sh` (проверка: бэкенд + фронт) и `bash scripts/restart.sh`
   в `mos_generated`; состояние — `scripts/healthcheck.sh`.
3. В Docker: оба репозитория рядом, из `mos_analiz_refactor` — `docker compose up -d --build`;
   `docker compose ps` → три сервиса healthy; `curl localhost:5174/api/health`.
   Правила и шаблоны — тома: после правки `docker compose restart api`, без пересборки.
4. Проверь пользовательский путь, не только health: логин → тип → файл → отчёт; генерация → docx.

## W8. Прочитать результат прогона

- Проверка: `logs_result/<тип>/session_<время>/` — `multi_rule_user_prompt.txt` (вход модели),
  `multi_rule_response_parsed.json` (вердикт по КАЖДОМУ правилу, в т.ч. пройденные),
  `*_methodology_*` (второй слой), `final_results.json` (только нарушения), `audit_result.xlsx`, `pipeline.log`.
  «Что модель сочла пройденным» есть только в `*_parsed.json`.
- Спецдвижки: `validation_report.xlsx` в сессии; `ERROR.txt` — если упал парсер.
- Генерация: `logs_generated/<тип>/session_<время>/` — `meta.json` (статус, клиент, размер), `values.json`, копия docx;
  отказы тоже там со `status: error`.
