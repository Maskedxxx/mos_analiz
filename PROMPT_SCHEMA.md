# Схема промпта multi-rule аудита

Для каждого документа выполняется **2 независимых LLM-вызова** (Qwen3.5-35B-A3B):
1. Базовый (менеджерский) слой — правила из `rules_multi.json`
2. Методический слой — правила из `rules_methodology.json`

Результаты обоих проходов объединяются с пометкой `layer: base | methodology`.

## Структура LLM-запроса

```
┌─ SYSTEM MESSAGE (одинаковый для обоих проходов) ────────────┐
│                                                             │
│ Ты — строгий аудитор документов.                            │
│ Один запрос = проверка сразу всех правил.                   │
│ Формат ответа: JSON-массив                                  │
│   [{rule_index, reasoning, verdict: {status, нарушения}}]   │
│ Правила поведения (не придумывать, опираться на текст и     │
│ секции, уважать target_section каждого правила)             │
│                                                             │
└─────────────────────────────────────────────────────────────┘

┌─ USER MESSAGE (собирается динамически) ─────────────────────┐
│                                                             │
│   ## FILENAME                                               │
│   <имя файла документа>                                     │
│                                                             │
│   ## DOCUMENT                                               │
│   <весь распарсенный текст документа>                       │
│                                                             │
│   ## SECTIONS  — семантическая карта секций                 │
│   - **шапка**: <описание>                                   │
│       start: <маркер начала>                                │
│       end: <маркер конца>                                   │
│   - **заголовок**: ...                                      │
│   - **распорядительная_часть**: ...                         │
│   - **блок_подписи**: ...                                   │
│   - ...                                                     │
│                                                             │
│   ## RULES  — ЗДЕСЬ РАЗВИЛКА ДВУХ ПРОХОДОВ                  │
│                                                             │
│   ### RULE <index> — <title>                                │
│   target_section: <название секции>                         │
│   check: <что именно проверить>                             │
│   exclusions: <что НЕ считать нарушением>                   │
│                                                             │
│   ### RULE <index> — <title>                                │
│   ...                                                       │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## Развилка двух проходов

В блоке `## RULES` — **только эта часть** отличается между вызовами:

### Проход 1 — базовый (менеджерский)

Источник: `doc_configs/<type>/rules_multi.json`
Индексы: обычно 1-99
Что проверяют: реквизиты, структуру, заполненность полей, подписанта

Пример (`prikaz_otvetstvennyh`):
```
### RULE 2 — Проверка заголовка приказа
target_section: заголовок
check: Тематическая строка содержит указание на назначение
       ответственных лиц за реализацию Программы.
exclusions: —

### RULE 3 — Проверка ПРИКАЗ/номер/дата
target_section: шапка
check: Присутствует слово «ПРИКАЗ», номер приказа и дата.
exclusions: Номер приложения не засчитывается как номер приказа.

### RULE 6 — 5 ответственных ролей
target_section: раздел_1_ответственные
check: Назначены 5 ролей с должностью и ФИО.
exclusions: Плейсхолдеры вместо реальных данных — не норма.
```

### Проход 2 — методический

Источник: `doc_configs/<type>/rules_methodology.json`
Индексы: от 100+
Что проверяют: требования из МР/МУ ФЦК

Пример (`prikaz_otvetstvennyh`):
```
### RULE 101 — Методика: контакты у 5 ролей
target_section: раздел_1_ответственные
check: Для каждой из 5 ролей указаны должность, ФИО,
       мобильный телефон, адрес электронной почты.
exclusions: Нескольких телефонов на роль допустимо.

### RULE 102 — Методика: ИТ-платформа производительность.рф
target_section: раздел_2_обязанности_руководителя
check: Есть пункт о работе с ИТ-платформой
       «Производительность.рф».

### RULE 103 — Методика: 3 обязательных приложения
target_section: приложения
check: Приложены: (№1) состав РГ, (№2) перечень курсов,
       (№3) план ключевых задач.
```

## Формат ответа LLM

Массив JSON, по одному объекту на правило:

```json
[
  {
    "rule_index": 2,
    "reasoning": "Краткое обоснование...",
    "verdict": {"status": "ok"}
  },
  {
    "rule_index": 3,
    "reasoning": "Номер приказа отсутствует...",
    "verdict": {
      "status": "fail",
      "нарушения": [
        {"Целевой документ": "№___", "Различие": "Номер пуст"}
      ]
    }
  },
  {
    "rule_index": 101,
    "reasoning": "Все 5 ролей имеют телефоны и email...",
    "verdict": {"status": "ok"}
  }
]
```

## Где что лежит

| Файл | Назначение |
|---|---|
| `audit_engine/multi_rule.py` | Runner: сборка промпта, LLM-вызов, парсинг |
| `audit_engine/engine.py` | Оркестратор: два прохода, merge violations |
| `doc_configs/<type>/sections.json` | Семантическая карта секций (для обоих проходов) |
| `doc_configs/<type>/rules_multi.json` | Базовые правила (1-99) |
| `doc_configs/<type>/rules_methodology.json` | Методические правила (100+) |

## Ключевое

- Оба прохода используют **одну и ту же карту секций** (sections.json)
- Различие **только в списке правил** в блоке `## RULES`
- LLM не знает из какого слоя правило — это метка движка (`layer` в violations)
- В Excel и UI violations разделены по `layer` на «Формальные» и «Методические»
