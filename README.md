# МосАнализ — проверка документов по правилам с помощью языковой модели

Сервис принимает документ (DOCX, PPTX, PDF-скан или XLSX-форму), набор правил для его типа и
возвращает отчёт в Excel: по каждому правилу — пройдено или нарушение, с цитатой из документа и
обоснованием. Языковая модель подключается по OpenAI-совместимому API (vLLM, llama.cpp, Ollama —
любой сервер с `/v1/chat/completions`). Типы документов и правила описываются JSON-файлами,
без кода.

Для стенда заказчика (МосМониторинг) сервис проверяет документы предприятий-участников
нацпроекта «Производительность труда» по методикам РЦК. Заведён 31 тип документов.

## Как это работает

```
файл + тип документа
  │
  ├─ гейт формата: допустимые расширения — из parser_by_ext в config.json типа
  ├─ парсер формата → полный текст документа            src/format_parsers/ (docx, pptx, pdf→OCR)
  ├─ сборка промпта: имя файла + текст + карта секций + правила   src/llm/multi_rule.py
  ├─ вызов модели, два прохода: базовые правила и методические
  ├─ разбор JSON-вердиктов → список нарушений
  └─ Excel-отчёт (все правила, статус ОК / FAIL)             src/audit/excel_reporter.py
       + артефакты прогона в logs_result/<тип>/session_<время>/
```

Второй путь — **спецдвижки** для табличных форм (карточка проекта, формы «в цифрах»,
план-график, КПСЦ, листы присутствия): парсер XLSX → Python-валидаторы → тот же Excel-отчёт.
Модель они вызывают точечно или не вызывают вовсе. Подробно — `docs/ARCHITECTURE.md`.

## Требования

| Что | Версия | Зачем |
|---|---|---|
| Python | 3.12 | бэкенд и CLI |
| Node.js | 20+ (проверено на 22) | сборка веб-интерфейса |
| LibreOffice (`soffice`), poppler-utils | любые актуальные | конвертация DOCX/PPTX → PDF → PNG для OCR |
| LLM-сервис | OpenAI-совместимый `/v1` | обязателен |
| OCR-сервис (VLM, OpenAI-совместимый `/v1`) и layout-детектор | | нужны только для PDF-сканов и картинок в шапке DOCX |

Без OCR и layout-сервисов работают все типы, у которых в `parser_by_ext` нет `.pdf`.

## Быстрый старт (5 минут)

```bash
git clone <repo> mos_analiz && cd mos_analiz
python3 -m venv .venv && .venv/bin/pip install -r requirements-dev.txt
cp .env.example .env            # заполнить: AUDIT_* (логин/пароль/токен), LLM_BASE_URL, LLM_MODEL
.venv/bin/python main.py --list-types
.venv/bin/python main.py --doc-type akt_nachala \
    --target doc_configs/akt_nachala/template/template.docx --session-dir /tmp/akt
ls /tmp/akt/audit_result.xlsx    # отчёт
```

Веб-интерфейс:

```bash
cd ui-demo && npm ci && cd ..
bash scripts/restart_all.sh      # бэкенд :8081 + фронт :5174 в screen-сессиях, затем healthcheck
```

Открыть `http://localhost:5174/`, войти логином и паролем из `.env`.

## Запуск в Docker (весь стенд одной командой)

Нужен Docker 24+ с Compose v2. Репозиторий генерации должен лежать рядом: `../mos_generated`
(compose собирает его образ сервисом `gen`).

```bash
cp .env.example .env             # AUDIT_*, LLM_BASE_URL, LLM_MODEL, при необходимости OCR_*/LAYOUT_*
docker compose up -d --build     # api :8081, gen :8090, ui :5174 (nginx: /api → api, /gen → gen)
docker compose ps                # все три — healthy
curl -s http://localhost:5174/api/health
```

Что монтируется томами (правится без пересборки): `doc_configs/` (типы и правила — после правки
`docker compose restart api`), `logs_result/`, `uploads/`, у генерации — `templates/`,
`logs_generated/` и стор значений по организациям. Адреса модели и OCR внутри контейнера — те же
`LLM_BASE_URL`/`OCR_BASE_URL` из `.env`: если модель на хосте, укажите `http://host.docker.internal:<порт>/v1/`
(Docker Desktop) или адрес хоста в сети. Порты наружу меняются переменными `API_PORT`, `GEN_PORT`, `UI_PORT`.
Остановить: `docker compose down` (тома с данными остаются).

## Если не запускается

| Симптом | Причина и что делать |
|---|---|
| `docker compose up`: `unable to prepare context: path "…/mos_generated" not found` | Не склонирован репозиторий генерации: он должен лежать рядом — `../mos_generated` |
| `docker compose ps`: `api` (или `gen`) в состоянии `Restarting` | Смотреть `docker compose logs api`; чаще всего в `.env` не заданы `AUDIT_LOGIN` / `AUDIT_PASSWORD` / `AUDIT_TOKEN` |
| Сервер сразу завершился с «не заданы переменные окружения …» / `[env] ВНИМАНИЕ: нет .env` | `cp .env.example .env` и заполнить `AUDIT_*` |
| `/api/health` отвечает 503 и `status: degraded`; `docker compose ps` показывает `unhealthy`; `scripts/healthcheck.sh` даёт код 1 | В `services` виден сервис со `status: error` и его `url` — проверить `LLM_BASE_URL`, `OCR_BASE_URL`, `LAYOUT_BASE_URL` в `.env` (адрес, порт, доступность из контейнера — `host.docker.internal`). Без OCR и layout работают все типы без `.pdf` |
| `scripts/restart_backend.sh` пишет «порт занят процессом <PID> (<команда>) — наш процесс не поднялся» | Порт держит чужой процесс (старый прод, забытый uvicorn): остановить его или задать другой `API_PORT`; то же для `UI_PORT` и `GEN_PORT` |
| В интерфейсе «Сервер недоступен, попробуйте позже» | Бэкенд не запущен или прокси `/api` смотрит не на его порт (`ui-demo/vite.config.js`, в Docker — `nginx.conf`) |
| Аудит завершается «Сервер языковой модели недоступен…» при зелёном health | Модель отвечает на `/models`, но не на запросы — смотреть лог сервера модели; таймаут — `OPENAI_TIMEOUT_SEC` |

Логи процессов: `$LOG_DIR/backend.log`, `frontend.log` (по умолчанию `/tmp`); в Docker — `docker compose logs <сервис>`.

## Конфигурация — переменные окружения

Все значения — в `.env` в корне проекта (образец `.env.example`), приоритет: переменная
процесса > `.env` > значение по умолчанию в коде.

| Переменная | Что | По умолчанию |
|---|---|---|
| `AUDIT_LOGIN`, `AUDIT_PASSWORD`, `AUDIT_TOKEN` | вход в веб-интерфейс и токен сессии | нет — без них сервер не стартует |
| `LLM_BASE_URL` | адрес модели до `/v1/` | `http://127.0.0.1:11437/v1/` |
| `LLM_MODEL` | имя модели, как отдаёт `GET /v1/models` | `Qwen3.6-35B-A3B` |
| `LLM_API_KEY` | ключ; для локальных серверов любое непустое | `none` |
| `LLM_MAX_TOKENS`, `LLM_SEED`, `OPENAI_TIMEOUT_SEC` | лимит ответа, seed, таймаут одного запроса (худшее ожидание аудита = таймаут × 3 повтора клиента × 5 попыток × 2 слоя) | 4096, 42, 300 |
| `LLM_CONTEXT_TOKENS` | размер контекста модели в токенах; документ больше — отклоняется до вызова модели с понятным текстом (оценка 3 символа на токен) | 262144 |
| `LOGS_MAX_GB`, `UPLOADS_MAX_GB` | лимиты `logs_result/` и `uploads/` в ГБ; при превышении удаляются самые старые сессии целиком (0 — не чистить), см. «Где логи» | 5, 1 |
| `OCR_BASE_URL`, `OCR_API_KEY`, `LAYOUT_BASE_URL` | OCR-модель и layout-детектор для PDF | `127.0.0.1:11438`, `none`, `127.0.0.1:11439` |
| `CORS_ORIGINS` | адреса фронтенда через запятую | `http://localhost:5174,http://127.0.0.1:5174` |
| `API_HOST`, `API_PORT`, `UI_PORT`, `NODE_VERSION`, `LOG_DIR` | параметры скриптов запуска | `127.0.0.1`, 8081, 5174, —, `/tmp` |

Код конфигурации: `config/llm.py` (модель) и `config/parsers.py` (парсеры, OCR). Остальные
параметры парсеров (DPI, пороги детекции) — там же, с описанием каждого поля.

## Свой тип документа

Тип = папка в `doc_configs/<имя>/` с `config.json`, картой секций `sections.json` и правилами
`rules_multi.json` (плюс необязательные `rules_methodology.json`, `rules_custom.json`).
Код писать не нужно: тип подхватывается сканом каталога. Пошагово — **`docs/ADD_DOC_TYPE.md`**.

образец презентации для smoke-тестов парсера; нужен.

## Использование

**CLI** — `python main.py --doc-type <тип> --target <файл> [--session-dir <папка>] [--out-xlsx <путь>]`.
Ещё: `--list-types`, `--parse-only` (только парсинг), `--print-prompts` (показать промпты без
вызова модели), `--rule-filter <индекс>` (одно правило), `--fail-on-violations` (exit 1 при нарушениях).

**HTTP API** (все, кроме `health` и `login`, требуют cookie или `Authorization: Bearer <AUDIT_TOKEN>`):

| Метод и путь | Что |
|---|---|
| `GET /api/health` | состояние сервера и внешних сервисов (LLM, OCR, layout) с их адресами; HTTP 200 — всё доступно, 503 — `degraded` (какой сервис упал — в `services`) |
| `POST /api/login` `{login, password}` | cookie сессии |
| `GET /api/types` | типы документов с допустимыми расширениями |
| `GET /api/types/{тип}/rules`, `POST …/rules`, `POST …/rules/draft` | правила типа; добавление кастомного; черновик формулировки через модель |
| `POST /api/audit` (multipart: `file`, `doc_type`) | запуск, возвращает `session_id` |
| `POST /api/audit/cross` (multipart: `files[]`) | сквозная сверка комплекта: ровно 3 разных файла, иначе 400 |
| `GET /api/audit/{id}/events` | SSE-прогресс |
| `GET /api/audit/{id}/result` | 202 пока идёт; затем `{violations, rules_checked, duration_sec, warnings, unchecked}`; при ошибке 500 `{detail, technical}`; сессии переживают рестарт (`session.json`) |
| `GET /api/audit/{id}/download` | Excel-отчёт |

**Артефакты прогона** — `logs_result/<тип>/session_<время>/`: `multi_rule_user_prompt.txt`
(что получила модель), `multi_rule_response_parsed.json` (вердикт по каждому правилу, включая
пройденные), `multi_rule_methodology_*` (второй слой), `final_results.json` (только нарушения),
`audit_result.xlsx`, `pipeline.log`, `original/` (загруженный файл), `session.json` (итог для `/result`
после рестарта). Если аудит упал — `ERROR.txt` с причиной и traceback (он же дописан в `pipeline.log`).

**Отчёт Excel** — 8 колонок: №, Проверка, Тип проверки (базовая / методическая), Статус (ОК / FAIL),
Источник (МР/МУ), Целевой документ (цитата), Различие, Обоснование.

## Ограничения и ожидания (для пользователя)

**Какой файл можно загрузить** — зависит от типа (подсказка показывается в интерфейсе после выбора типа,
API отдаёт список в `GET /api/types` → `allowed_extensions`):

| Типы | Форматы |
|---|---|
| Приказы, положения, акт, протокол, справка, чек-лист, отчёт о результатах опроса (0.1, 0.2 приказ, 0.5, 0.6, 1.3, 1.5, 1.6, 2.2, 2.5 чек-лист, 3.3, 3.5, 3.10) | `.docx`, `.pdf` (скан — через OCR) |
| Карточки проекта 0.2 и 2.4, формы 0.3 и 0.4, драйверы 1.1, КПСЦ 2.1, план-график 2.6, листы присутствия 3.1 и 3.4 | `.xlsx` |
| Презентации 2.5 и 2.8 | `.pptx` |
| Приказ о проведении выхода 3.6 | `.docx`, `.pdf`, `.xlsx` (график обхода) |
| Сквозная сверка | ровно три файла: карточка 2.4 (`.xlsx`), протокол 0.6 и приказ 0.5 (`.docx`) |

Файл проверяется до запуска: пустой, повреждённый, защищённый паролем, старого формата (`.doc`/`.xls`)
или другого типа внутри (например, таблица Excel под именем `.docx`) отклоняется сразу с объяснением.

**Сколько ждать.** Двухстраничный `.docx` — около 30–35 секунд (два прохода модели: базовые и методические
правила); двухстраничный скан — около минуты (плюс OCR); большие документы — минуты. Аудиты выполняются
**по одному**: если сервер занят, экран показывает позицию в очереди. На шаге «Проверка правил» видно, что
ждём ответ модели и какая это попытка (при нечитаемом ответе модель переспрашивается до 5 раз). Если модель
молчит, ожидание ограничено `OPENAI_TIMEOUT_SEC` (см. конфигурацию) — потом придёт понятная ошибка, а не
вечный спиннер; при обрыве соединения интерфейс сам переспросит результат и восстановит его после `F5`.

**Размер.** Ограничения по мегабайтам нет; предел — контекст модели (`LLM_CONTEXT_TOKENS`, при оценке
3 символа на токен ≈ 250 страниц текста). Больший документ отклоняется до вызова модели с текстом
«Документ слишком большой для проверки…».

**Отчёт.** Правила, по которым модель не дала вердикт, помечены «НЕ ПРОВЕРЕНО» (в интерфейсе — блок
«Не проверено: N правил»), а не выдаются за пройденные; предупреждения парсера (не распознанные страницы,
битый файл пользовательских правил) — на листе «Предупреждения».

**Что означает ошибка на экране** (техническая причина — под «Подробности», для администратора):

| Текст | Что делать |
|---|---|
| Файл пустой / повреждён / не является документом … / защищён паролем или сохранён в старом формате / Внутри файла — таблица Excel, а не документ Word | Пересохранить документ в нужном формате и загрузить снова |
| Неподдерживаемый формат файла «…». Для типа «…» допустимы: … | Выбрать другой тип или формат (таблица выше) |
| Документ не удалось распознать, проверка не выполнена | В файле нет текста (пустой документ, пустой скан) или не распознались все страницы — проверить документ; если это скан, администратору проверить OCR и layout в `/api/health` |
| Документ слишком большой для проверки | Разделить документ или убрать приложения |
| Сервер языковой модели не ответил за отведённое время / недоступен или не отвечает / вернул ошибку (код …) | Повторить позже; администратору — `LLM_BASE_URL` и `/api/health` |
| Модель «…» не найдена на сервере языковой модели | Администратору — `LLM_MODEL` |
| Модель не вернула результат в ожидаемом формате после 5 попыток / вернула ответ в неожиданном формате | Повторить проверку; если повторяется — администратору (сырой ответ в `multi_rule_response_raw.txt` сессии) |
| Сервис распознавания сканов недоступен | Администратору — `OCR_BASE_URL`, `LAYOUT_BASE_URL` |
| Ошибка записи на сервере (нет прав или места на диске) | Администратору — место на диске, права на `logs_result/`, `uploads/` |
| Тип документа не найден / настроен некорректно | Администратору — `doc_configs/<тип>/` (в `--list-types` тип помечен «НЕДОСТУПЕН: причина») |
| Файл пользовательских правил повреждён | Администратору — восстановить `rules_custom.json` из `.bak` рядом; аудит при этом идёт по базовым правилам с предупреждением |
| Сервер недоступен, попробуйте позже | Бэкенд не запущен или прокси `/api` смотрит не туда — раздел «Если не запускается» |
| Сессия истекла (перевод на экран входа) | Войти заново — токен сменился или сервер перезапущен |

**Где логи и при каком объёме чистятся.** Артефакты каждой проверки — `logs_result/<тип>/session_<время>/`
(см. «Артефакты прогона»); загруженный файл после аудита лежит там же в `original/`, каталог `uploads/<id>/`
живёт только пока аудит выполняется. При старте сервера и раз в сутки проверяется объём: пока `logs_result/`
больше `LOGS_MAX_GB` (по умолчанию 5) или `uploads/` больше `UPLOADS_MAX_GB` (1) — удаляются самые старые
сессии целиком (вместе с `original/`); выполняющиеся не трогаются; `0` отключает очистку. Что удалено —
строка `[RETENTION]` в логе процесса. Логи процессов: `$LOG_DIR/backend.log`, `frontend.log`
(по умолчанию `/tmp`), в Docker — `docker compose logs api`.

## Регресс после правок

```bash
bash scripts/regress_api.sh doc_configs/akt_nachala/template/template.docx akt_nachala   # аудит через API: нарушения, правила, отчёт
bash scripts/regress_cross.sh <карточка.xlsx> <протокол.docx> <приказ.docx>            # сквозная сверка
```

Снять числа до правки, повторить после — число правил и структура отчёта должны совпасть.


Тесты спецдвижков ждут образцы в `tests/data/<тип>/sample.xlsx` (в git нет — документы с
персональными данными; без них пропускаются). Откуда взять — `tests/data/README.md`.
`tests/test_kpsc_parsers.py` требует каталог `test_docs/` с реальными КПСЦ.

## После правок

Python не подхватывает изменения на лету — после правки кода или правил перезапустить бэкенд:
`bash scripts/restart_backend.sh`. Фронт после правок в `ui-demo/`: `bash scripts/restart_frontend.sh`.
