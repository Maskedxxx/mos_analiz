# Архитектура сервиса проверки документов

## 1. Узлы пайплайна

| Узел | Модуль | Принимает | Отдаёт | При ошибке |
|---|---|---|---|---|
| Определение движка | `src/engines.py::detect_engine` | `doc_type` | ключ спецдвижка или `vision` (generic) | нет `config.json` → generic |
| Гейт формата | `src/api/server.py::_get_allowed_extensions` | `doc_type` | набор расширений из `parser_by_ext` (спецдвижки — `.xlsx`) | расширение не в наборе → 400 до загрузки |
| Загрузка конфига типа | `src/audit/models.py::load_audit_config` | папка типа | `AuditConfig` | `parser_by_ext` и `engine` заданы оба или ни один → `ValueError` |
| Парсер формата | `src/format_parsers/{docx,pptx,pdf}` | путь к файлу, конфиг парсера | `{filename, path, raw_text}` | исключение парсера → сессия в статусе `error`, лог в `pipeline.log` |
| Правила и секции | `src/llm/multi_rule.py::load_multi_rule_config`, `load_methodology_config` | папка типа | `{sections, rules, include_scopes}`; кастомные правила из `rules_custom.json` мёрджатся на каждом прогоне | нет `sections.json`/`rules_multi.json` → `ValueError` с текстом |
| Сборка промпта и вызов | `src/llm/multi_rule.py::run_multi_rule_audit` | текст, секции, правила, имя файла | `{verdicts, violations, usage}` | ответ модели не разбирается → до 5 повторов со сменой seed, берётся лучший |
| Клиент модели | `src/llm/client.py::make_llm_client` | `base_url`, `api_key` (из `config/llm.py`) | `OpenAI` с таймаутом | сеть/таймаут → `APIConnectionError` наверх |
| Excel-отчёт | `src/audit/excel_reporter.py::save_to_excel` | нарушения + все правила | `audit_result.xlsx`, 8 колонок, статус ОК / FAIL по каждому правилу | — |
| Оркестратор generic | `src/audit/engine.py::AuditEngine.run` | путь к файлу, параметры | `AuditResult` | пишет `ERROR` в лог сессии, пробрасывает |
| Спецдвижок | `src/doc_type_validators/<тип>.py::run_*_special` | `args` (target, session_dir, doc_type, …) | `AuditResult` + `validation_report.xlsx` | ошибка парсинга → `ERROR.txt` в сессии, статусы `ERROR` в отчёте |
| Веб-слой | `src/api/server.py` | HTTP | JSON, SSE-события, файл отчёта | 401 без токена, 202 пока идёт, 500 при падении аудита |

Артефакты каждого прогона: `logs_result/<тип>/session_<время>/` — промпты обоих слоёв, сырые
и разобранные ответы, `final_results.json`, `audit_result.xlsx`, `pipeline.log`, `parsed_docs/`.

## 2. Два движка

**Generic (LLM).** Признак — `parser_by_ext` в `config.json`. Документ читается целиком в текст,
модель получает один промпт: имя файла, текст, карту секций и список правил, и возвращает
JSON-массив вердиктов (по объекту на правило). Правил в промпте столько, сколько в файле;
модель вызывается дважды — базовый слой (`rules_multi.json`) и методический
(`rules_methodology.json`), результаты объединяются с пометкой слоя.

**Спецдвижки (Python).** Признак — `engine` в `config.json`, значение — ключ в
`src/engines.py::SPECIAL_ENGINE_RUNNERS`. Табличные формы читаются парсером в JSON, затем
набор функций-валидаторов даёт статус по каждому правилу. Модель используется точечно
(семантические проверки в карточке проекта и КПСЦ) через `call_llm`.

**Сквозная сверка** — спецдвижок над несколькими файлами: раскладка по ролям по ключевым словам
имени, общий контекст, один вызов модели с правилами кросс-проверки.

## 3. Модель и параметры вызова

Единственное место создания клиента — `src/llm/client.py` (`make_llm_client`,
`make_async_llm_client`); адрес, ключ и имя модели — `config/llm.py`, читается из `.env`.
Прямые вызовы `chat.completions.create` с особыми параметрами живут в `multi_rule.py`
(temperature 0.7, top_p 0.8, top_k 20, seed фиксирован и меняется при повторе, `max_tokens`
64000), в `crosscheck.py` и в авторе правил (`server.py`). Во всех вызовах передаётся
`chat_template_kwargs: {enable_thinking: false}` — режим рассуждений Qwen ломает строгий JSON.
Имена облачных моделей из старых конфигов (`gpt-*`, `openai/*`) подменяются на текущую
(`resolve_runtime_llm_model`).

## 4. Веб-интерфейс

`ui-demo/` — React + Vite. В продакшене отдаётся `vite preview`, который проксирует `/api` на
бэкенд проверки и `/gen` на сервис генерации документов (отдельный репозиторий, порт 8090;
префикс срезается, потому что оба бэкенда отдают `/api/types/*`). Сайдбар переключает
«Аудит» и «Генерация»; экран аудита при переключении не размонтируется — SSE-прогресс не рвётся.

## 5. Ключевые решения (ADR, кратко)

**ADR-1. Два движка вместо одного.** Табличные формы содержат числа и формулы; модель проверяет
их ненадёжно, Python — детерминированно. Текстовые документы, наоборот, требуют понимания
формулировок. Цена: два способа описать тип (JSON-правила против кода валидатора) и общий
реестр, который должен быть согласован с конфигами (закрыто тестом `test_registry.py`).

**ADR-2. Правила — в JSON, не в коде.** Правила пишет и правит эксперт-методолог; итерация
доводки — правка текста `check`/`exclusions` и повторный прогон, без программиста. Цена:
качество зависит от формулировок, нужен бенчмарк для контроля ложных срабатываний.

**ADR-3. Два прохода модели: базовый и методический слой.** Формальная структура документа и
требования методик — разные источники и разные авторы; раздельные проходы дают короче промпт,
меньше взаимного влияния правил и отдельную колонку в отчёте. Цена: два вызова на документ.

**ADR-4. Конфигурация — Python-модули с pydantic-settings.** Дефолты и описание каждого поля
рядом с кодом, автодополнение; переносимость — через переменные окружения и `.env`, без
правок кода и конфигов типов. Цена: новая переменная требует правки модели конфига.

**ADR-5. Один документ — один промпт со всеми правилами.** Дешевле и стабильнее, чем вызов
на правило: модель видит контекст целиком, а порядок правил задаёт порядок вердиктов.
Цена: длинные документы и большие наборы правил упираются в контекст; при «каше» в ответе
делается повтор со сменой seed.
