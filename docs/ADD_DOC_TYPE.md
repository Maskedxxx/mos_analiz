# Как добавить свой тип документа

Тип документа — папка в `doc_configs/<имя_типа>/`. Код не нужен: сервис сканирует каталог при
каждом запросе списка типов. Ниже — два сценария: текстовый документ, проверяемый моделью
(основной), и табличная форма с Python-валидатором (спецдвижок).

## 1. Текстовый документ (DOCX / PPTX / PDF) — проверка моделью

### Шаг 1. Папка и `config.json`

```
doc_configs/prikaz_example/
  config.json
  sections.json
  rules_multi.json
  rules_methodology.json      (необязательно — второй слой правил)
  template/template.docx      (необязательно — образец для smoke-тестов)
```

`config.json`:

```json
{
  "doc_type": "prikaz_example",
  "doc_title": "4.1 Приказ об утверждении регламента",
  "parser_by_ext": { ".docx": "docx", ".pdf": "paddle" },
  "temperature": 0.0,
  "max_workers": 1
}
```

| Поле | Обязательно | Что |
|---|---|---|
| `doc_type` | да | совпадает с именем папки |
| `doc_title` | да | название в интерфейсе; код в начале («4.1 …») задаёт порядок в списке |
| `parser_by_ext` | да | какие расширения принимаются и каким парсером читаются: `docx`, `pptx`, `paddle` (PDF через OCR). Расширения не из списка отклоняются ещё до загрузки |
| `filename_keywords` | нет | используется только спецдвижком листов присутствия (проверка имени файла); generic-движок поле не читает, имя файла и так передаётся модели в промпте |
| `temperature`, `max_workers` | нет | параметры прогона; по умолчанию 0.0 и 1 |
| `model`, `llm_base_url`, `llm_max_tokens`, `llm_seed`, `reasoning_effort` | нет | переопределения общего конфига для одного типа. Обычно не нужны — модель задаётся через `.env` |
| `secondary_file` | нет | второй файл к документу (`{type, parser, chunk_prefix}`), используется редко |

Поле `engine` для текстовых типов **не** задаётся (см. §2).

### Шаг 2. `sections.json` — карта документа

Модель ищет каждое правило в указанных секциях, поэтому документ надо разметить на смысловые
блоки. Описываются границы, а не текст:

```json
{
  "sections": {
    "заголовок":      { "description": "Название документа: «ПРИКАЗ …».", "start": "начало документа", "end": "перед номером и датой" },
    "реквизиты":      { "description": "Номер, дата, город.", "start": "строка с номером", "end": "перед преамбулой" },
    "основной_текст": { "description": "Пункты приказа.", "start": "слово ПРИКАЗЫВАЮ", "end": "перед подписями" },
    "подписи":        { "description": "Должность, подпись, ФИО.", "start": "после последнего пункта", "end": "конец документа" }
  }
}
```

Имена секций — произвольные, на них ссылаются правила. 4–8 секций достаточно.

### Шаг 3. `rules_multi.json` — базовые правила

```json
{
  "include_scopes": null,
  "rules": [
    {
      "index": 1,
      "title": "Номер и дата приказа",
      "target_sections": ["реквизиты"],
      "check": "В реквизитах указаны номер приказа и дата в формате «ДД.ММ.ГГГГ» или «ДД месяц ГГГГ г.». Отсутствие номера или даты — нарушение.",
      "exclusions": "Формат номера (с буквами, дробью) — не нарушение."
    },
    {
      "index": 2,
      "title": "Подпись руководителя",
      "target_sections": ["подписи"],
      "check": "В блоке подписей есть должность и ФИО руководителя. Нет должности или ФИО — нарушение."
    }
  ]
}
```

| Поле правила | Что |
|---|---|
| `index` | уникальный номер внутри файла; базовые — 1…99, методические — 101…199, кастомные (через интерфейс) — от 200 |
| `title` | короткое название, попадает в отчёт |
| `target_sections` | где искать; список имён из `sections.json`. Все секции — если правило про документ в целом |
| `check` | что проверить и **когда считать нарушением** — самая важная часть. Пишется как инструкция проверяющему: критерии по пунктам, каждый с явным условием нарушения |
| `exclusions` | что нарушением **не** является (снимает ложные срабатывания) |

Как писать `check`: описывать структуру блока абстрактно («есть строка должности и строка ФИО»),
а не цитировать конкретный документ; каждое условие — с исходом «… — нарушение».
Правила про правильность значений формулировать через согласованность и формат, а не через
«истинность» (модель не знает внешних фактов).

### Шаг 4. `rules_methodology.json` — методический слой (необязательно)

Тот же формат, плюс шапка с источником. Это второй проход модели — требования из методических
документов заказчика, отдельно от формальных проверок структуры:

```json
{
  "layer": "methodology",
  "source": "Методические рекомендации МР-XX-2026, раздел 4",
  "include_scopes": null,
  "rules": [
    { "index": 101, "title": "Методика: срок исполнения", "target_sections": ["основной_текст"],
      "check": "...", "exclusions": "...", "source_ref": "МР-XX п. 4.2", "nature": "обязательно" }
  ]
}
```

В отчёте такие правила помечены типом «Методическая».

### Шаг 5. Проверить

```bash
# 1. Конфиги валидны, тип виден:
.venv/bin/pytest -q tests/test_smoke_configs.py -k prikaz_example
.venv/bin/python main.py --list-types | grep prikaz_example

# 2. Посмотреть, что получит модель (без вызова):
.venv/bin/python main.py --doc-type prikaz_example --target <файл.docx> --print-prompts

# 3. Прогон:
.venv/bin/python main.py --doc-type prikaz_example --target <файл.docx> --session-dir /tmp/t
cat /tmp/t/multi_rule_response_parsed.json     # вердикт по каждому правилу
open /tmp/t/audit_result.xlsx

# 4. Веб: перезапустить бэкенд — тип появится в списке
bash scripts/restart_backend.sh
```

Доводка правил — по артефактам прогона: если правило срабатывает ложно, уточнить `check` и
`exclusions`; если пропускает — сузить `target_sections` и добавить явное условие нарушения.
Кастомные правила, добавленные через интерфейс, попадают в `rules_custom.json` того же типа
(индексы от 200) и подхватываются без перезапуска.

## 2. Табличная форма (XLSX) — спецдвижок с Python-валидатором

Когда проверка — не про текст, а про ячейки и формулы (заполнены ли строки, сходятся ли суммы),
модель не нужна. Для такого типа пишется парсер и набор валидаторов.

1. **`doc_configs/<тип>/config.json`** — вместо `parser_by_ext` задаётся `engine`:
   ```json
   { "doc_type": "forma_example", "doc_title": "5.1 Форма примера", "engine": "forma_example" }
   ```
   Рядом — `validation_rules.json` с описанием правил (свободная структура, см. `doc_configs/forma_0_3/validation_rules.json`).
2. **Парсер** `src/doc_type_parsers/forma_example.py`: XLSX (openpyxl) → JSON с нужными полями.
3. **Валидатор** `src/doc_type_validators/forma_example.py`: функции `_rule_N_validate(data, rule) -> dict`
   со статусом `PASS`/`FAIL` и раннер `run_forma_example_special(args) -> AuditResult`, который
   парсит, прогоняет правила и пишет `validation_report.xlsx` в `args.session_dir`. Образец —
   `src/doc_type_validators/forma_0_3.py`.
4. **Реестр** — одна строка в `src/engines.py`:
   ```python
   "forma_example": run_forma_example_special,
   ```
   Один раннер может обслуживать несколько типов (как карточки 0.2 и 2.4) — тогда он различает
   их по `args.doc_type`.
5. **Проверка:** `pytest -q tests/test_registry.py` (реестр ↔ конфиги), затем образец в
   `tests/data/forma_example/sample.xlsx` и `pytest -q tests/test_smoke_special_xlsx.py` — если
   добавить строку с новым типом в параметры теста.

## 3. Сквозная сверка комплекта

Тип с `engine: crosscheck_…` принимает несколько файлов сразу и раскладывает их по ролям по
ключевым словам имени (`required_docs` в `config.json`), затем один вызов модели с правилами
из `rules.json`. Образец — `doc_configs/crosscheck_2_4_0_6_0_5/` и
`src/doc_type_validators/crosscheck.py`.
