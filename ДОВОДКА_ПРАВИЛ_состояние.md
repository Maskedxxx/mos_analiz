## 1. О чём вообще задача

**Чек-сервис «МосАудит»** проверяет типовые документы проекта по производительности труда
(приказы, положения, акты, протоколы, чек-листы, формы) на соответствие методике и находит ошибки.

Есть **бенчмарк** (`~/projects/_benchmark/`): эксперты разметили реальные документы —
на каждый тип обычно **4 «плохих» (BAD)** дока с намеченными ошибками + **2 «эталонных» (OK)** без ошибок.

**Задача кампании:** довести правила КАЖДОГО типа до «идеальной метрики»:
- все BAD ловят свои **покрываемые** размеченные ошибки (на уровне правил);
- оба OK-эталона **чисты** (0 ложных срабатываний базового слоя);
- часть ошибок эксперта — принципиально некатчабельны (корректность значения без эталона)
  или ошибочно размечены (mismark) — их **осознанно исключаем**, не выдумывая оверфит-правил.

Делаем **по одному типу за итерацию**, не перепрыгивая.

## 2. Как устроен чек-сервис (минимум для понимания)

- Репозиторий: `~/projects/mos_analiz_refactor` (на dev-стенде `ms-llm-dev`, доступ — инструмент `dev`).
- Правила по каждому типу: `doc_configs/<тип>/`:
  - `rules_multi.json` — **base**-правила (структура, реквизиты) — по ним считается основная метрика;
  - `rules_methodology.json` — **meth**-правила (соответствие методичке, строже, справочные; часто вне экспертного скоринга);
  - `sections.json` — карта секций документа (модель получает её как подсказку «где что искать»);
  - `config.json` — тип движка (`generic` = LLM-проверка; иначе — special-раннер).
- Движок посылает модели **весь текст документа** + карту секций + список правил.
  По каждому правилу модель отвечает `ok` / `fail` + обоснование. В результат попадают только `fail`.
- Правило смотрит в `target_section(s)` — это **подсказка**, а не фильтр (модель видит весь док).

### Как гонять и смотреть результат
```
# прогон одного типа через бенчмарк (свежий процесс — всегда актуальный код+правила):
rm -rf ~/projects/_benchmark/results/<тип>
cd ~/projects/mos_analiz_refactor && screen -dmS run bash -c \
  ".venv/bin/python ~/projects/_benchmark/run_batch.py --only <тип> --scope score > /tmp/run.log 2>&1"
# вердикт по КАЖДОМУ правилу (в т.ч. ok) — в сессии:
#   results/<тип>/<сессия>/multi_rule_response_parsed.json      (base)
#   results/<тип>/<сессия>/multi_rule_methodology_response_parsed.json (meth)
# final_results.json — ТОЛЬКО нарушения (для агрегата, не для «что ok»).
```

## 4. Методика доводки одного типа

Подробно — в скиле `mosanaliz-tune-playbook` (на стенде `~/.claude/skills/mosanaliz-tune-playbook/SKILL.md`).
Кратко цикл:

1. **Фаза 0** — собрать корпус ≥10 доков типа из всех источников в `~/projects/_corpus/<тип>/` (бенчмарк + прод `~/projects/mos_analiz` + логи юзерских загрузок).
2. **Фаза A** — аудит легитимности всех правил на корпусе (проверяет реально присутствующее? смотрит в ту секцию? не требует отсутствующего?).
3. **Агент-ревьюер #1** — независимо перепроверяет легитимность и катчабельность (сам читает доки/правила).
4. **Тюнинг (Шаги 1-10):** прогон эталонов → маппинг ошибок эксперта на правила → секция → root-cause → хирургичный фикс с бэкапом → перепрогон → сверка → регресс.
5. **Агент-ревьюер #2** — гейт качества (7 проверок): фикс ловит цель, нет оверфита/размывания, эталон не сломан, полнота, чтение верное.
6. **Коммит** — с апрувом владельца.

### Пограничные кейсы — как решали (важно, §3.12-3.17 скила)
- «Значение неверно» (дата/год) — часто это **консистентность полей**, а не абсолютная корректность → формализуется (дата начала ≥ даты приказа; дата шапки = дата конца периода). Ловит BAD, чисто на эталоне.
- «Нет блока/таблицы X» — **сначала посмотреть docx-таблицы / глазами**: часто блок ПО ФАКТУ есть (mismark эксперта) или у эталонов ровно так же (не обязателен). Правило под mismark не добавлять.
- Правило смотрит не в размеченную секцию → **добавить секцию в `sections.json` / нацелить `target_sections`** (не размывать текст правила).
- Правило требует того, чего нет почти ни в одном доке корпуса → **удалить правило**.
- **Город=Москва** — согласованный проектный хардкод: «если указан — = Москва; отсутствие — норма». Риск для регионов зафиксирован.
- **Типы-близнецы** (prikaz_ic ↔ prikaz_ic_potoka) — переиспользовать отлаженные формулировки, но перепроверять на СВОИХ эталонах.
